# Планирование закупок импортёра

## Что это

По выгрузке ERP считает, что, сколько и когда заказывать у поставщиков из Китая (плечо 4–6 месяцев).
Результат — `out/dashboard.html` для закупщика и `plan.csv`, `risks.csv`, `summary.md`.
Модель пишет пояснения, но цифры считает только код.

## Как устроено

| Модуль `zakupki/` | Что делает |
|---|---|
| `config.py` | все пороги (`Config`) и названия статусов |
| `data.py` | чтение и проверка CSV, обрезка по дате расчёта, «Качество данных» |
| `demand.py` | спрос по месяцам, упущенный спрос при нулевом остатке |
| `forecast.py` | сезонные индексы категорий, уровень, тренд, прогноз на 36 месяцев |
| `supply.py` | плечо, надёжность поставщиков, заказы в пути, кратность, остаток сейчас |
| `simulation.py` | остаток по месяцам, дата обнуления, страховой запас, дата заказа |
| `plan.py` | количество к заказу, статусы, риски, календарь |
| `explain.py` | пояснения: модель через OpenAI-совместимый API или шаблон; кэш |
| `history.py` | снимки в `out/history/<дата>/`, сравнение с прошлым запуском |
| `backtest.py` | точность прогноза: прогноз со среза на 12 мес. назад против продаж после него, WAPE и bias против M12 и LY (только дашборд) |
| `dashboard.py` | HTML-дашборд из `templates/dashboard.html` |
| `report.py`, `cli.py` | `summary.md`; команда запуска |
| `notify.py` | сводка из `summary.md` в Telegram после пересчёта |

Промпты модели — в `zakupki/prompts/`, навык — `.claude/skills/plan-zakupok/`.

## Команды

Запускать из корня проекта.

```
python -m zakupki run --data data/raw/share --today 2026-08-13 --no-llm   # exit 0, 791 SKU, к заказу 41 335 шт. (сейчас 34 994)
python -m ruff check zakupki tests && python -m pytest -q                   # 226 passed
python -m pytest -q tests/test_plan.py                                      # один файл
python -m zakupki run --data DIR [--today YYYY-MM-DD] [--out out] [--no-llm] [--min-markup N] [--cover-days N] [--z N]
```

- Повторный запуск с теми же аргументами: «Что изменилось: новых к заказу 0…», `plan.csv` и `risks.csv` побайтно те же.
- Результат — в `out/` (в git не лежит); снимки — `out/history/<дата>/`, кэш модели — `out/llm_cache.json`.
- Регулярный запуск: `scripts/run_daily.ps1 -Today 2026-08-13` (без параметра берёт `$env:DATA_DATE`; журнал — `out/run_daily.log`).
- Linux: `scripts/cron.example` — `DATA_DATE` подставляется в `--today`, если задана.
- CI: `.github/workflows/plan.yml` — plan → deploy → notify: выгрузка берётся из репо (`data/raw/share/`, новая выгрузка — коммитом), `DATA_DATE` из поля ручного запуска или переменной репозитория, пустая → без `--today`; дашборд публикуется на Pages; `out/history` переживает запуски через `actions/cache`; notify шлёт сводку в Telegram (`python -m zakupki.notify`).

## Окружение

Читается из `.env` в текущей папке (образец `.env.example`); переменные окружения главнее файла.

- `LLM_BASE_URL` — адрес OpenAI-совместимого API (к нему добавляется `/chat/completions`).
- `LLM_API_KEY` — ключ доступа к API.
- `LLM_MODEL` — имя модели для пояснений.
- Любая из трёх пуста или `--no-llm` — пояснения шаблонные, расчёт не меняется.
- Модель пишет только для статусов ЗАКАЗАТЬ СЕЙЧАС и РИСК ДЕФИЦИТА; сбой API → шаблон.
- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` — для `python -m zakupki.notify`; не заданы — уведомление пропускается (код 0).
- `DATA_DATE` — дата расчёта ГГГГ-ММ-ДД для `scripts/run_daily.ps1`, cron и workflow; в `--today` её передают они, сам CLI её не читает.

## Подводные камни

- Без `--today` дата расчёта — по последнему заказу или приходу (на этой выгрузке 01.08.2026, а не 13.08); CLI пишет предупреждение в stderr.
- Шаблон `zakupki/templates/dashboard.html` и промпты `zakupki/prompts/` ищутся от расположения пакета и входят в wheel (`package-data` в `pyproject.toml`). `.env` и `out/` — от текущей папки, поэтому запускать из корня.
- Выгрузка `data/raw/share` лежит в git (обезличенная, из тестового задания); остальное в `data/` не отслеживается; `tests/test_real_data.py` без выгрузки пропускается.
- Windows + Docker: ruff даёт EXE002 на всех файлах (бит исполняемости при монтировании) — `--extend-ignore EXE002`.
- Тесты не ходят в сеть: autouse-фикстура в `tests/conftest.py` чистит `LLM_*` и подменяет `urlopen`.
- Страховой запас в днях ограничен плечом (`safety_days` не больше `lead_days`, `simulation.py`).
- Дефицит в `risks.csv` — только если РИСК ДЕФИЦИТА основной статус (у МЁРТВЫЙ, НИЗКАЯ НАЦЕНКА и НЕТ НАЦЕНКИ строки нет).
- Избыток считается с учётом заказов в пути: остаток плюс в пути должен быть больше 0.
- Просрочка больше `overdue_stale_days` (90 дн.) — не «в пути» и не приход (`stale` в `supply.open_orders`), только риск ПРОСРОЧЕН ЗАКАЗ.
- Пустая наценка ≠ нет продаж: МЁРТВЫЙ — только без чистых продаж за `dead_window_months` полных месяцев, иначе НЕТ НАЦЕНКИ (нет себестоимости в ERP).

## Правила

- Цифры считает только код; модель получает готовые числа и пишет текст.
- Пороги и константы — только в `zakupki/config.py`, в остальных модулях числовых порогов нет.
- Расчёт детерминирован: даты из `cfg.today`, без `date.today()`, сортировки устойчивые. Время запуска — только подпись «пересчитано» в шапке дашборда, передаёт `cli.py`; в расчёт и CSV не идёт.
- `data/raw/` только читается. Зависимости: pandas, numpy; HTTP — `urllib`.
- Комментарии и тексты для пользователя — по-русски, коротко; имена в коде — по-английски.
- Ошибки данных — `DataError` с русским сообщением, CLI выходит с кодом 2.
- Тесты — на синтетических данных из `tests/conftest.py`; ключей и значений секретов в коде нет.

## Как здесь работает Autopilot

Сборка ведётся навыком `/autopilot`. Требования, спецификация и таски — в `.autopilot/`.
Прогресс — `.autopilot/dashboard.html`. Требование из `manifest.md` может снять
только пользователь. Прерванную сборку продолжает «продолжи автопилот».

### Правка без автопилота

Мелкий баг или доводка после сборки — обычная сессия, без прогона.

Сначала прочитай:
1. `.autopilot/PROGRESS.md` — что не доделано, известные баги, о чём договорились с пользователем.
2. Что правили после последней сборки — первая строка таблицы в «История git».
3. Только если правка их касается: почему сделано так — `docs/adr/`; что значат слова — `CONTEXT.md`;
   что именно просили — `manifest.md` в папке сборки (указана в начале `PROGRESS.md`).

После правки:
- коммит — по правилам из «История git»;
- строка в «Правки без автопилота» в `PROGRESS.md`: дата — что — почему;
- починенный пункт из «Не доделано» или «Известные баги» — удали;
- договорились с пользователем о том, что следующая сборка не должна пересматривать, —
  строка в «Договорились», его словами.

### История git

Целиком не читай — бери срез под вопрос:

| Вопрос | Команда |
|---|---|
| что правили после последней сборки | `git log --oneline "$(git log -1 --format=%h --grep='^Autopilot: сборка сдана')"..HEAD -- . ':(exclude).autopilot'` |
| всё, что делали ради требования | `git log --oneline --grep="R02"` |
| история файла | `git log --oneline -10 -- <файл>` |
| когда появился или исчез код | `git log --oneline -S "<фрагмент>"` |
| почему строка такая | `git blame -L <с>,<по> <файл>`, затем `git show <sha>` |
| что внутри коммита | `git show --stat <sha>` |

Срез длиннее ~30 коммитов — отдай его субагенту и возьми выжимку в десять строк.

Коммит: заголовок — что (`fix: даты в одном формате`), тело — почему, трейлер
`--trailer "Requirements: R02"`, если правка касается требования из `manifest.md`.
Заголовок `Autopilot: сборка сдана` пишет только автопилот — по нему находят последнюю сборку.
