# Бриф: ИИ-система планирования закупок (импортёр)

## Кто заказчик и что нужно

Компания-импортёр: электроинструмент, садовое оборудование, сантехника из Китая.
Срок поставки 4–6 месяцев. Каждый месяц закупщики решают, что и сколько заказать,
чтобы покрыть спрос и не перегрузить склад. Сейчас это долго: надо учесть историю
и динамику продаж, популярность, сезонность, остатки и заказы в пути.

Система должна по данным определять:
1. какие товары закупить;
2. в каком количестве разместить заказ;
3. на какой период хватит текущих запасов с учётом размещённых заказов;
4. когда размещать следующий заказ;
5. по каким позициям риск дефицита или избытка.

Сдаём:
1. **Дашборд** (ссылка) — наглядно: что заказать, сколько и когда; полная картина
   предстоящих закупок, чтобы принять решение.
2. **Видео** (пишет Вадим) — инструмент, структура проекта, `CLAUDE.md`, Skills,
   промпты. Поэтому `CLAUDE.md`, навык в `.claude/skills/` и промпты в `prompts/` —
   часть результата, а не служебные файлы: понятные, по-русски, без воды.
3. **Регулярный запуск** — не разовый анализ: одна команда пересчитывает всё
   по обновлённым данным (ежедневно или по запросу) и показывает, что изменилось
   с прошлого запуска.

## Данные

`data/raw/share/` — реальная обезличенная выгрузка из ERP дистрибьютора.
**Сначала прочитать `data/raw/share/README.md` целиком** — там смысл колонок
и ловушки. Коротко:

| Файл | Что |
|---|---|
| `sku_dim.csv` | 791 SKU, 6 категорий, поставщик, `supply_type`, `target_cover_days` (0 = не задано), `avg_markup_pct_12m` (пусто = не продавался 12 мес), `on_order_qty` |
| `sales_monthly.csv` | продажи помесячно 2020-11…2026-08, плотный календарь (0 = честный ноль), `qty_returned` не вычтен, `partial_month=1` — неполный месяц, в средние не брать |
| `stock_monthly.csv` | остаток на 1-е число, только с 2024-01 |
| `purchase_orders.csv` | заказы поставщикам: `open` (в пути), `completed`, `closed` (часто частично); `planned_lead_days`, `promised_date`, `qty_pending` |
| `receipts.csv` | фактические приходы |
| `supplier_dim.csv` | поставщики, медианы плеча и ритма приходов |

Факты из данных (проверено):
- сезонность по категориям (доля годовых продаж по месяцам):
  `space_heaters` — окт 36%, ноя 19%, янв 15%, апр–авг ≈0;
  `string_trimmers` — май 28%, июн 20%; `trimmer_blades_accessories` — май 33%, июн 22%;
  `concrete_mixers` — мар–авг 10–13%, дек 1%; `sanitary_faucets`, `grain_mills` — ровно;
- открытых заказов 57, в ожидании 20 039 шт.;
- последний снимок остатков — 2026-08 (315 SKU); данные на 2026-08-13;
- плечо: медиана планового 123 дня, p25 52, p90 205;
- наценка < 25% у 68 SKU из 413 продававшихся; 378 SKU не продавались 12 мес.

**«Сегодня» для расчёта = дата данных (2026-08-13), параметром.** Не системная дата.

## Правила расчёта (решения, не обсуждать заново)

Цифры считает детерминированный код (pandas). **Модель ничего не считает** — только
объясняет готовые цифры закупщику. Один и тот же вход → один и тот же план.

1. **Спрос ≠ продажи.** Месяц с нулевыми продажами при нулевом остатке на начало
   месяца (с 2024-01, где есть остатки) — упущенный спрос: не ноль, а пропуск,
   восполняется по сезонному профилю. Спрос = `qty_sold − qty_returned` (не меньше 0).
   Неполный месяц отбрасывается.
2. **Прогноз с сезонностью.** Сезонный индекс по категории (по всем полным годам),
   уровень SKU — по последним 12 полным месяцам, очищенным от сезонности; тренд —
   сглаженный, с ограничением. Горизонт — 12 месяцев вперёд, помесячно. Для SKU
   с короткой историей (< 12 мес) — индекс категории + среднее за то, что есть,
   с пометкой «мало истории».
3. **Плечо по SKU.** Медиана `planned_lead_days` по заказам этого SKU, иначе —
   поставщика (`supplier_dim`), иначе 123 дня. Ограничить 30…210.
4. **Надёжность поставщика.** Доля поставленного: `qty_received / qty_ordered`
   по закрытым и исполненным заказам. Заказы в пути учитываются с этим
   коэффициентом. Показать в дашборде.
5. **Заказы в пути.** `status=open`, `qty_pending > 0`. С `promised_date` в прошлом —
   «просрочен», считать, что придёт через 30 дней, и вывести в рисках.
   Повторно уже заказанное не заказывать.
6. **Симуляция запаса** помесячно на 12 мес: остаток − прогноз + приходы по датам.
   Отсюда: на сколько месяцев/дней хватит (покрытие с учётом заказов в пути),
   месяц обнуления.
7. **Когда заказывать.** Дата = дата обнуления − плечо − страховой запас.
   Страховой запас: `z=1.65` × σ месячного спроса × √(плечо в мес.).
8. **Сколько.** Прогноз на (плечо + период покрытия) + страховой − остаток −
   в пути (с надёжностью). Период покрытия: `target_cover_days`, если > 0, иначе 90 дней.
   Не меньше 0, округлить вверх; если есть кратность партий по `receipts` — до неё.
9. **Статусы SKU** (у каждого ровно один основной + флаги):
   - `ЗАКАЗАТЬ СЕЙЧАС` — дата заказа ≤ сегодня + 30 дней;
   - `ЗАПЛАНИРОВАТЬ` — дата заказа в пределах 12 мес;
   - `ЗАПАС В НОРМЕ`;
   - `РИСК ДЕФИЦИТА` — обнулится раньше, чем успеет прийти заказ, сделанный сегодня
     (докупить не успеваем: показать, сколько месяцев «дыры»);
   - `ИЗБЫТОК` — покрытие > плечо + покрытие + 6 мес (заморожены деньги);
   - `НИЗКАЯ НАЦЕНКА` — `avg_markup_pct_12m` < `MIN_MARKUP_PCT=25`: **в автозакупку
     не попадает**, отдельный список «пересмотр цены / вывод»;
   - `МЁРТВЫЙ` — нет продаж 12 мес (пустая наценка): не закупать, отдельный список,
     если есть остаток — «распродать»;
   - флаг `МАЛО ИСТОРИИ`.
   Все пороги — в одном конфиге, не размазаны по коду.
10. **Пояснения (ИИ).** Для строк «заказать сейчас» и «риск» — 1–2 предложения
    закупщику (почему, что учтено: сезон, в пути, надёжность) + общая сводка
    на 5–7 строк по всему плану. Вызов через OpenAI-совместимый API
    (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` из `.env`). Нет ключа или ошибка —
    шаблонное пояснение из цифр, расчёт от этого не зависит. Промпт — в
    `prompts/explain.md`. В промпт идут только цифры и id, без лишнего.

## Дашборд

Одна статичная HTML-страница (`out/dashboard.html`), открывается без сервера,
данные внутри, графики — одна библиотека с CDN (Plotly или Chart.js).
- шапка: дата данных, сколько SKU заказать сейчас / запланировать / риск / избыток /
  низкая наценка / мёртвые; штук к заказу всего;
- главная таблица «Что заказать»: SKU, категория, поставщик, статус, сколько,
  до какой даты, покрытие (мес.), в пути, плечо, пояснение. Сортировка, фильтр по
  категории и статусу, поиск по SKU, выгрузка в CSV;
- календарь заказов: по месяцам на 12 мес — сколько позиций и штук разместить;
- риски: дефицит (с месяцами «дыры»), избыток, просроченные заказы поставщиков;
- отдельные списки: низкая наценка, мёртвый ассортимент;
- по клику на SKU — график: история спроса, прогноз, остаток в симуляции, приходы;
- сезонность категорий (12 месяцев, доли);
- блок «Что изменилось с прошлого запуска»;
- сводка ИИ сверху.
Мобильная ширина не обязательна, но таблица не должна ломаться.

## Регулярный запуск

- `python -m zakupki run --data data/raw/share --today 2026-08-13` → `out/`
  (dashboard.html, plan.csv, risks.csv, summary.md) + снимок в `out/history/<дата>/`;
- сравнение с предыдущим снимком → «что изменилось» (новые к заказу, сдвинулись
  даты, ушли из риска);
- `scripts/run_daily.ps1` (Windows Планировщик) и пример cron / GitHub Actions;
- `README.md`: как обновить данные и запустить, 10 строк.

## Структура и качество

- Python 3.12, pandas, numpy, pytest; код — пакет `zakupki/` по модулям:
  загрузка и проверка данных, спрос, прогноз, поставки, план, пояснения, дашборд, CLI.
- Тесты pytest на ключевую логику: упущенный спрос, сезонность (обогреватели
  к октябрю должны заказываться весной–летом, а не по среднему), заказы в пути
  не заказываются повторно, низкая наценка не попадает в автозакупку, мёртвые
  распознаются, просроченный заказ уходит в риски, детерминизм.
- Проверка на реальных данных: прогон по всему набору без ошибок, сводка цифр
  в `out/summary.md`.
- `CLAUDE.md` в корне: что за проект, как устроен, как запускать, правила
  (цифры — только код, пороги — в конфиге). Навык `.claude/skills/plan-zakupok/SKILL.md`:
  как запустить анализ, как читать результат, как поменять параметры.
- Никаких следов «сгенерировано ИИ» в комментариях. Комментарии по-русски, коротко.

## Что НЕ делаем

- Нет веб-сервера, базы данных, авторизации.
- Нет ML-фреймворков (prophet, sklearn и т.п.) — хватает сезонных индексов.
- Нет денежных сумм (в данных их нет).
- Не трогать файлы в `data/raw/`.
